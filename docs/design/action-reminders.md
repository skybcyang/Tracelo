# 待办负责人、行动安排与提醒

2026-10-16。本轮为交互设计，不是实现或安装记录。

## 确认范围

用户以 PL＋PM 身份管理版本、团队事务，并参与问题解决、方案、计划、会议、材料及活动组织。已明确希望待办中的 `@某人` 表达该待办负责人，并要求设计卡片内主动添加提醒及按日期提示行动的能力。

以下具体语法边界、布局、时间默认值和智能安排均为提案，未视为用户确认。用户“如何只能提醒哪天应该做什么”暂按“如何智能提醒哪天应该做什么”理解。

## 1. 待办里的 @负责人

- 示例：`@张三 输出接口联调结论`，保存后显示负责人标签和行动正文；负责人可出现在行中任意位置，以明确的人员标记识别。
- 输入 `@` 展示当前任务目录曾用人员，可选或新增；人员选择器提供“我”。无需团队账号或通讯录授权。没有 @ 时显示无负责人，避免把所有未分配事项推断成自己的承诺。
- 简单姓名使用 `@姓名`，以空白或标点结束；复杂姓名由选择器生成完整标记。保存前显示解析结果，中文组合输入期间不提交或替换输入节点。邮箱、网址及代码里的 @ 不解析为负责人。
- 首版每条待办一位负责人；出现多位时保留输入并要求选定负责人或拆分，不静默采用第一个。普通提及别人使用姓名文本，@ 明确表示分配。
- 负责人标签与正文使用同一份持久化语义，保证 Markdown 往返及直接编辑可解释。改名不意外改变其他同名人员；具体协议和稳定人员身份在实施前确定。
- 该语法仅用于待办；右侧工作对话的 `@任务` 继续表示任务引用。
- 负责人是个人工作台中的责任记录，不表示已向对方发送任务、对方已接受或会自动收到通知。通知收件人始终是当前用户。

## 2. 三种时间分开

| 信息 | 回答的问题 | 行为 |
| --- | --- | --- |
| 计划日 | 哪天准备做这一步？ | 加入所选日期的行动列表，不自动弹通知 |
| 提醒时间 | 什么时候提醒我做或跟进？ | 日期＋时间到达后通知，可稍后提醒或改期 |
| 截止日 | 最晚哪天交付整个任务？ | 沿用任务截止语义及日历，不自动当成开始日 |

日期均显示本地实际年月日；计划日、截止日为日历日期，提醒需明确时区及时间。相对日期解析后保存具体值，不随打开日期漂移。只写“周五做”产生计划日候选；“周五提醒我”需展示明确时间，可使用用户设置的默认时间，但不得悄悄补一个时间保存。无默认时间时让用户选择。

## 3. 在卡片里添加提醒

展开卡片或选中任务展示台内提供轻量“添加提醒”文字入口；待办行菜单提供“安排日期／提醒我”。没有提醒的收起卡片不增加空区或重复按钮。已有提醒在收起卡片显示最近一项的日期摘要，展开后查看全部；封面流模式的具体位置随工作台设计确认，不恢复已移除的进展摘要。

添加时使用内联小表单：提醒内容、日期、可选具体时间、保存。默认关联当前任务；从待办进入时绑定该待办的稳定身份并带入正文，改写提醒文案不修改待办。支持任务级独立提醒，例如“检查版本整体风险”，不强制先造一条待办。

负责人为别人时默认文案为“跟进张三：输出接口联调结论”；负责人为自己时为“处理：输出接口联调结论”；未指定负责人时使用中性文案并允许修改。具体日期和完整动作在保存前可见。

示例：

```text
任务：V2.3 联调验收
☐ 输出接口联调结论   [张三] [计划 周四]
  🔔 周五 10:00 · 跟进张三的联调结论

🔔 周五 16:00 · 检查版本遗留风险
```

同一待办首版只保留一个有效提醒，可改期，不因重复点击新增副本；任务可以有多条不同内容的独立提醒。删除或更改负责人时同步更新显示，用户自定义提醒文案不静默改写；若内容可能不一致，在编辑处提示核对。

## 4. 哪天应该做什么

在现有右侧日期区增加“当日行动”内容，与现有当日截止列表明确区分，保留周历、日期切换和截止入口。候选展示位置不代表玻璃工作台右侧栏已确认。

- 我来做：明确负责人是我，且安排在所选日期的待办。
- 我要跟进：所选日期的跟进提醒，即使事项由别人负责。
- 其他安排：无负责人或他人负责、只有计划日的待办，标明人员，不冒充我的行动。
- 待处理提醒：之前已提醒但未处理的内容，不自动修改原计划日或截止日；提供改期、关闭提醒和定位任务。

同一行动兼有计划和提醒时合并展示信息，不形成两条重复任务。切换右侧日期不筛掉左侧当前卡片。系统通知点击后定位任务及对应行动，保留当前编辑草稿，不修改对话引用。

智能建议只在用户请求“帮我安排”后生成，使用当前任务或用户明确选定的任务；每日行动列表按已保存信息聚合，无需模型。模型不得因此读取全库、文件夹材料或其他会话。

建议要列出“行动、日期、原因”，例如“周五交评审稿，建议周三形成初稿，周四预留修改”；没有工期和空闲信息时明确这是建议，不能声称已避开会议或排出了可靠工期。用户确认单项后保存，初版沿用既有逐项确认写入，不自动排序、高亮或批量修改任务。

第一阶段提供人工设置与明确时间表达的预览确认；跨任务智能建议作为后续选项。输入普通日期不直接创建承诺或提醒。

## 5. 提醒后的闭环及可靠性

- 系统通知提供打开事项入口；事项内提供“已处理／稍后提醒／改期”。关闭通知只关闭展示，不勾选待办；关闭独立提醒只结束该提醒，不完成任务。勾选关联待办后撤销其未触发提醒；取消勾选时不恢复旧的过期提醒，提供重新安排入口。
- 完成或异常关闭任务，停止该任务全部未来提醒；重开保留记录，但不自动重放旧提醒。删除待办撤销关联提醒，撤销删除时已过期的提醒需要重新确认。动作、安排变更与通知投递状态分开，不把发送通知写成正式进展。
- 到点提醒一次，不因没有处理持续弹窗。相近时间的多项提醒合并；过去未处理事项留在列表。稍后提醒明确下次触发时间，重试与重复启动不能重复投递同一次提醒。
- 插件负责编辑和展示，本机快捷程序拟负责后台调度及系统通知，避免两端各弹一次。需在实施阶段验证两平台原生通知能力、数据读取与同步协议。Obsidian 关闭但快捷程序运行时应可提醒；两者都未运行、设备关机或睡眠时，不承诺准点提醒，恢复后合并提示错过事项。权限未开、同步待确认及调度不可用须显示真实状态，不能仅凭保存表单显示“提醒已生效”。
- 提醒日期变更、时区变化及休眠恢复需重新核对调度；提醒保存失败保留表单。待办变更继续采用既有稳定身份及并发保护。取消、结束、改期与即将投递之间需要最终状态校验，避免取消后迟到通知。
